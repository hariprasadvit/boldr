# 07 · Decision Log (ADR-style)

Short records of the load-bearing decisions and *why*, so a new joiner doesn't re-litigate them.

## ADR-001 — Provider-agnostic LLM via LangChain → OpenRouter (no vendor SDK)
**Decision:** all LLM calls go through LangChain's `init_chat_model` pointed at OpenRouter's
OpenAI-compatible endpoint. Model/provider is chosen by env (`OPENROUTER_MODEL`).
**Why:** avoid lock-in to any single provider SDK (Anthropic *or* OpenAI). LangChain gives a
uniform `BaseChatModel` interface (structured output, retries, message types) and composes with
LangGraph. OpenRouter gives one key + model fallback + transparent caching across providers.
**Rejected:** the Anthropic SDK (vendor-bound), the raw OpenAI SDK (also vendor-bound, even if
pointed at OpenRouter). **Implication:** set `OPENROUTER_API_KEY`; model slugs are dotted
(`anthropic/claude-sonnet-4.6`).

## ADR-002 — FastAPI + React (Vite), not Next.js
**Decision:** the go-forward app is a Python FastAPI backend that serves a Vite-built React SPA.
**Why:** we want **LangGraph (Python)** as the real engine, and we want a **single process**.
Next.js is a Node server — it can't run Python in-process, so Next.js + Python is always ≥2
runtimes. Vite/React is a *build tool*: it emits static files that one FastAPI process can serve
alongside the API. → single process, Python brain, modern UI.
**Implication:** host on Render/Railway/Fly/VM/containers, **not Vercel** (no persistent Python).
The existing `web/` Next.js app becomes legacy.

## ADR-003 — Postgres + pgvector (one database)
**Decision:** store relational data **and** KB embeddings in one Postgres (pgvector extension).
**Why:** the brief needs durable state (tickets, runs, gaps, approvals, run history) that a
vector store + CSVs can't provide. Putting embeddings in the same Postgres means one thing to
run/back up/deploy. Embeddings generated by **fastembed** (ONNX, no torch).
**Rejected:** keep ChromaDB separate (two stores to operate). Vector store stays behind a
`VectorStore` interface so the choice remains swappable.

## ADR-004 — Real human-in-the-loop now (not a status flag)
**Decision:** implement the approval queue with LangGraph `interrupt()` + a **Postgres
checkpointer** so a draft genuinely pauses execution, persists, and resumes on approval.
**Why:** it's the brief's core requirement and the biggest gap in the legacy code (where
"approval" was a CSV label + a disabled button). Doing it properly now avoids a rewrite later.
**Implication:** every ticket is a resumable thread keyed by `ticket_id`; needs the DB (Phase 4).

## ADR-005 — Backend first, then React
**Decision:** build the whole backend (all endpoints working, testable via `/docs`) before the UI.
**Why:** a stable API contract lets the frontend be built once against something real; avoids
churn. **Implication:** interim testing is via Swagger `/docs`, not a UI.

## ADR-006 — `uv` for Python environments
**Decision:** use `uv` for all Python dependency/venv management (engine and backend).
**Why:** fast, reproducible, lockfile-based; the user's standard. **Implication:** `uv sync`,
`uv run ...`; Python pinned to 3.13 via `.python-version` (3.14 lacks some wheels).

## ADR-007 — Async SQLAlchemy 2.0 + Alembic
**Decision:** async SQLAlchemy (psycopg3) with Alembic migrations; engine created lazily so the
app boots without a live DB. **Why:** production-grade, scalable, idiomatic with FastAPI; lazy
engine keeps local dev/health usable before Postgres is up.

## ADR-008 — Vercel-only deployment, no Docker (amends ADR-002/003)
**Decision:** target **Vercel** as the only deploy target; **no Docker** anywhere. The repo is
one Vercel project: the built React app is served as Vercel static assets, and FastAPI runs as a
**Python serverless function** handling `/api/*`. Locally it's a single uvicorn process serving
both API and the static build.
**Why:** the user's hosting choice. FastAPI *does* run on Vercel (as serverless functions via an
ASGI entrypoint) — this reverses the earlier "Vercel can't host Python" caution; what it can't
host is a *persistent* server, which we don't need because state lives in Postgres.
**Consequences (the serverless constraints we must design around):**
- **DB:** no local Docker Postgres → use a **managed serverless Postgres with pgvector** (Neon /
  Vercel Postgres). Use the **pooled** connection string on Vercel.
- **HITL still works:** `interrupt()` + the **Postgres** checkpointer persist state to the DB, so
  pause/resume survives across stateless invocations.
- **Embeddings:** running a local ONNX/torch embedder in a serverless function is impractical
  (size/cold-start) → prefer an **embeddings API** at request time; KB vectors are precomputed at
  seed time. (Provider pending — see open questions; the chosen dim sets the `vector(N)` column.)
- **Heavy/long jobs** (clustering, marketing brief, benchmark) don't fit a request handler →
  run via **Vercel Cron** functions (which also satisfies the brief's weekly/monthly cadence) or
  offline, writing results to Postgres. Keep request-path deps lean (mind the 250 MB function limit).
**Tooling:** **uv** for the backend, **pnpm** for the frontend.

## ADR-009 — Neon · dedicated embeddings API · offline batch jobs (resolves ADR-008 open items)
**Decisions:**
- **Database host: Neon** (managed serverless Postgres + pgvector). No Docker; same connection
  string for local dev and prod. Use the **pooled** host on Vercel.
- **Embeddings: a dedicated API** (Jina / Voyage / Cohere) behind an `EmbeddingClient` interface.
  Default `jina-embeddings-v3` (1024-d). Needs `EMBEDDING_API_KEY`. The dim sets the
  `kb_chunks.embedding vector(N)` column — changing provider/dim ⇒ new migration.
- **Heavy intelligence jobs run offline** (`uv run python -m app.scripts.*`) and write results to
  Postgres; Vercel only reads. So `scikit-learn`/`pandas`/`numpy` live in an **`offline` uv
  dependency group**, kept out of the serverless function (size limit). Scheduling is external for
  now (manual / CI), which also covers the brief's weekly/monthly cadence.

## ADR-010 — Frontend is a faithful port of the existing `web/` UI (no redesign)
**Decision:** the new React + Vite frontend must reproduce the **exact UI/UX** of the current
Next.js app in `web/` at origin HEAD — same layout, styling, components, and copy, pixel-for-pixel.
This is an **architecture-only** migration (Next.js → React/Vite served by FastAPI); the look and
feel does not change.
**Why:** explicit user requirement. The `web/` UI is already clean/polished and is the design of
record.
**How:** port `web/app/*.tsx`, `web/app/components.tsx`, and `web/app/globals.css` (Tailwind)
into `frontend/src/` faithfully; only swap the data layer (Next API routes/`web/lib/*` → calls to
the FastAPI `/api/v1/*` endpoints). No new design work, no component restyling.

## ADR-011 — Pure Postgres (Neon-compatible); embeddings behind EmbeddingClient (provider TBD)
**Decisions:**
- **Postgres:** write **pure Postgres** (no Neon-specific features) → identical on a **local
  Postgres now** and **Neon free tier later** by swapping `DATABASE_URL`. `psql` is already installed.
- **Embeddings: via OpenRouter (RESOLVED).** OpenRouter *does* have an embeddings endpoint
  (`POST /api/v1/embeddings`, added 2026), so embeddings reuse the **same `OPENROUTER_API_KEY`** —
  one provider for chat *and* embeddings. Model: **`nvidia/llama-nemotron-embed-vl-1b-v2:free`**,
  output **2048-d** → `kb_chunks.embedding` is `vector(2048)`, `EMBEDDING_DIM=2048`. Implemented
  behind the `EmbeddingClient` interface (LangChain `OpenAIEmbeddings` pointed at OpenRouter). The
  model is vision-language but embeds text fine for KB retrieval; it's free-tier (mind rate limits).
- **Batch jobs:** keep the **current offline-script pattern** (today they're manual
  `python -m intelligence.*` scripts over CSV); upgraded to write to Postgres, kept in the
  `offline` uv dependency group (out of the Vercel function).
