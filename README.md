# Boldr Customer Intelligence Engine

A self-improving customer intelligence engine for Boldr Supply Co. — built for the
Echelon 2026 AI Workflow Competition.

### 🔗 Live app: **https://echelon-boldr.vercel.app**

**Not a chatbot.** Every customer enquiry becomes three things at once: a drafted
reply, a knowledge-base improvement, and a marketing signal.

## What it does

1. **Classify** — extracts question type, buyer persona, and escalation flags.
2. **Search** — vector retrieval (pgvector) over FAQ, product specs, and rate cards,
   re-ranked by source trustworthiness.
3. **Route** — confidence-thresholded auto-reply, human-review queue, or knowledge gap.
4. **Draft** — a brand-voice reply that cites its KB sources and never invents facts.
5. **Flag gaps** — novel questions get an auto-drafted KB entry for one-click approval.
6. **Cluster themes** — groups novel questions into themes.
7. **Marketing brief** — persona-tagged intelligence: what customers ask that the
   product pages don't answer.
8. **External benchmark** — cross-checks internal signals against external sentiment.

See [`PROBLEM_STATEMENT.md`](PROBLEM_STATEMENT.md) for the full walkthrough.

## Architecture

Single-process app: a **FastAPI** backend (Python, LangGraph → OpenRouter, async
SQLAlchemy) serves both the JSON API and the built **React + Vite** SPA from one
origin. Data lives in **Postgres + pgvector** (Supabase). Deployed on **Vercel**.

```
boldr/
├── backend/            # FastAPI app, LangGraph pipeline, repositories, services
│   ├── app/            # application code (api, agent, kb, intelligence, models…)
│   ├── api/index.py    # Vercel ASGI entrypoint
│   ├── data/           # source CSV/JSON/TXT (tickets, KB sources, personas)
│   ├── static/         # built SPA, served by FastAPI (committed)
│   ├── alembic/        # database migrations
│   └── tests/          # e2e API tests
├── frontend/           # React + Vite SPA (builds into backend/static)
├── vercel.json         # Vercel build config (root → backend Python function)
└── PROBLEM_STATEMENT.md
```

## Prerequisites

- **Python 3.13** and [**uv**](https://docs.astral.sh/uv/) (backend deps + runner)
- **Node 20+** and [**pnpm**](https://pnpm.io/) (frontend)
- A **Postgres database with the `pgvector` extension** (we use Supabase). You need
  two connection strings — async (asyncpg) for the app and sync (psycopg) for
  Alembic. Behind a transaction pooler (e.g. Supabase port 6543) the app disables
  prepared-statement caching automatically.
- An **OpenRouter API key** (used for both the chat model and embeddings).

## First-time setup

```bash
git clone git@github.com:dhinakaran-cms/echelon-boldr.git
cd echelon-boldr/backend

# 1. Install backend deps
uv sync

# 2. Configure environment
cp .env.example .env
#    Edit .env and set:
#      DATABASE_URL_ASYNC=postgresql+asyncpg://USER:PASS@HOST:6543/postgres
#      DATABASE_URL_SYNC=postgresql+psycopg://USER:PASS@HOST:5432/postgres
#      OPENROUTER_API_KEY=sk-or-...
#    (Supabase: use the POOLER host. The direct db.<ref> host is IPv6-only.)

# 3. Create tables + the pgvector extension
uv run alembic upgrade head

# 4. Seed source data, then build the KB and run the baseline pipeline
uv run python -m app.scripts.seed_all      # tickets, personas, KB chunks (embeds)
uv run python -m app.scripts.run_baseline  # runs the graph over seeded tickets
#    (intelligence artefacts — theme clusters, marketing brief, external bench —
#     are generated by the intelligence scripts / endpoints)
```

> **Seeding & migrations are run locally**, never on Vercel. The deployed function
> only *reads* the database.

## Run locally

```bash
# Backend API on http://localhost:8000  (docs at /docs)
cd backend
uv run uvicorn app.main:app --reload --port 8000

# Frontend dev server on http://localhost:5173 (proxies /api → :8000)
cd ../frontend
pnpm install
pnpm dev
```

Single-process (build the SPA into the backend and serve everything on :8000):

```bash
cd backend && make serve      # builds frontend → backend/static, then runs uvicorn
```

## Database: migrate & seed

| Task | Command (run from `backend/`) |
| --- | --- |
| Apply migrations | `uv run alembic upgrade head` |
| New migration | `uv run alembic revision --autogenerate -m "msg"` |
| Seed tickets/personas/KB | `uv run python -m app.scripts.seed_all` |
| Run baseline pipeline | `uv run python -m app.scripts.run_baseline` |

Everything is idempotent and points at the database in your `.env`. The embedding
dimension (`EMBEDDING_DIM`) must match the `kb_chunks.embedding` vector column.

## Deployment (Vercel)

The repo is connected to Vercel — **pushing to `master` triggers an automatic
production deploy**. How it builds:

- The **root `vercel.json`** builds `backend/api/index.py` as a `@vercel/python`
  serverless function and bundles `backend/{app,data,outputs,static}`.
- `backend/api/index.py` adds `backend/` to `sys.path` so imports resolve from the
  repo-root build context, then re-exports the FastAPI `app`.
- The **built SPA is committed** under `backend/static` and served by FastAPI
  (single origin). Rebuild it with `pnpm build` (or `make serve`) and commit when
  the frontend changes.
- **No build step runs on Vercel for the DB** — migrations and seeding are done
  locally against Supabase beforehand.

Required Production env vars in Vercel:

```
DATABASE_URL_ASYNC   DATABASE_URL_SYNC   OPENROUTER_API_KEY        # secrets
ENV  DEBUG  API_PREFIX  OPENROUTER_MODEL  OPENROUTER_BASE_URL
EMBEDDING_MODEL  EMBEDDING_DIM  KB_TOP_K  LOG_LEVEL  DB_POOL_SIZE
```

## Health checks

- `GET /api/v1/health` — liveness (does not touch the database)
- `GET /api/v1/health/db` — readiness (verifies the database connection)
